# dboss agent notes

Single Go binary (`dboss`) that supervises, proxies and logs the apps on one host.
Read `./README.md` for usage and the embedded configuration reference (`./internal/config/reference.yaml`, printed by `dboss config --reference`) before changing behavior.

## Deploy and configure

* Build once, then copy the binary to the box: `make build` produces `./bin/dboss`; install it at a stable path and pass that path to `dboss systemd --bin`. `~/bin/dboss` is only the local dev symlink and must not be used in a unit.
* Runtime deps on the box: Linux, `lsof` (a host start clears every listener in `ports`, `dboss kill` needs it too) and a writable `dir` (the runtime folder holding `state/`, `log/` and `dboss.sock`). Go is build-time only.
* Host config lives at `<dir>/dboss.yaml`: `management.host` + `management.admins` are the minimum for a real host (a dev session needs neither: it always gets the loopback console and signs a local request in), plus `tokens.dboss` when hooks or `/metrics` are used. Every other host key has a sane default (`apps: ./apps`, `dir: ./.dboss`, `proxy.listen: ":80"`, `ports`, `authcog_realm`, `maintenance_at`). The config has no tuning knobs: cadences, timeouts, rotation sizes and backoff are constants next to their code, and a dropped key fails `dboss check` through `movedKeys` in `./internal/config/keycheck.go`, which names its replacement. With no config file at all `dboss start` runs the default host. Validate with `dboss check -c <dir>/dboss.yaml` before starting.
* Server-only values (admin emails, secrets, absolute paths) go in `<dir>/dboss.local.yaml`. It wins over `dboss.yaml`, is gitignored, and is never touched by a deploy, so it is how box edits survive. The console's "Create server override" copies `dboss.yaml` to it.
* Install and enable the service: `sudo dboss systemd -c <dir>/dboss.yaml --user <svc> --bin <path> --install` writes `/etc/systemd/system/dboss.service`, reloads and enables it. `--user` defaults to `$SUDO_USER` (`defaultServiceUser`), never to the root that `--install` runs as, and a unit that would still run as root warns. The unit runs `dboss start` as `<svc>` from the config dir with `Restart=always`, `RuntimeDirectory=dboss`, `AmbientCapabilities=CAP_NET_BIND_SERVICE` (port 80 without root) and `LimitNOFILE=65536`. It also sets `Environment=PATH` with the service user's `~/.local/bin` first (`servicePATH`, so `mise` is found) and an `ExecStartPre=+` that hands that user `res.DefaultCgroupRoot`; without it `selectCgroup` falls back to procgroup and `memory`/`cpu` limits are silently ignored.
* `./install.sh` is the whole install path and never leaves a root-run daemon behind: no flag installs only the binary, `--dev` scaffolds a foreground host in `./dboss`, and `--server --user <svc>` scaffolds `/srv/dboss`, chowns it, runs `dboss check` and delegates the unit to `dboss systemd --install`. It never creates users; the deploy account is reused on purpose. Setup logic belongs there, not in the binary - the binary keeps owning behavior.
* `dboss deploy sync|git` (`./internal/cli/deploy.go`) are the built-in deploys, run from the app folder on the dev machine. `sync` ships `git ls-files --cached` only (tracked files; untracked and ignored files are never copied, a server-only file is placed on the box on purpose) with `rsync --files-from=-`, then runs `dboss deploy apply` over ssh, which deletes only files the previous manifest (`<app>/.dboss-sync`) listed and the new one does not (never `syncProtected`, never through a symlink), writes the manifest and restarts through the socket. rsync's own `--delete` is never used: openrsync (macOS) deletes gitignored files on the receiver. Everything placed on the ssh command line passes `remoteSafe`, since the remote shell parses it. `git` POSTs the `deploy` hook with `tokens.dboss` as a bearer and polls `GET /hooks/<app>/<hook>` (`handleHookStatus`) until `Running` and `Restarting` are both false. lux-deploy still works: it calls `dboss restart <app>` after its symlink swap (socket `/run/dboss/dboss.sock`). `dboss check` is the pre-deploy gate.
* `dboss add <url>` and the console's **Add app** dialog (`db-add-app.fez`, `POST /api/apps/add`) are one audited action, `ops.Service.add` (`./internal/ops/add.go`): `git.NormalizeRepo` (https/ssh/scp kept, `host/path` and `owner/repo` become https, local paths and other schemes refused), `config.ValidAppName`, refuse an existing folder, `git.Clone`, `config.FindInDir` + `ParseApp`, an optional host override written as a full-copy `dboss.local.yaml` through `config.PatchYAML` (one web process only), a host clash check against the live snapshots before `Rescan` (discovery hands a contested host to the first name), then `Start`. Every failure after the clone removes the folder with `apps.Destroy`. `git.AuthEnv` scopes the token helper to `https://github.com`, so no other host is ever offered `tokens.github`; the dialog's URL hint mirrors `NormalizeRepo` in JS and the server stays the authority.
* App config is `<app>/dboss.yaml`: a `procfile` is the minimum. A procfile entry is a command string (background process) or a `{command, hosts, pubsub, static, health, canonical_host, count}` mapping. Every entry that declares `hosts` is a web process and owns its hostnames, its static directory (`static`, default `./public`, `false` disables), its readiness path (`health`), its canonical hostname (`canonical_host`) and its `pubsub` hub; an app may have several web processes, each bound to its own port and host set. The console edits these same files on disk.
* Config lookup: `-c path`, then `$DBOSS_CONFIG`, then `./dboss.local.yaml` or `./dboss.yaml`. Every folder lookup goes through `config.FindInDir`, which falls back to `<dir>/config/` and refuses a folder with config files in both; `config.BaseDir` keeps the parent as `cfg.Dir` for a file found there, so relative paths, `.env` and `.dboss` stay in the app folder. Socket lookup: `--socket`, `$DBOSS_SOCKET`, the config's `socket` when it exists, then `/run/dboss/dboss.sock`.
* One file name, two roles: a file with `procfile:` is an app; any other file is a host (with `apps` defaulting to `./apps`), never both. `defaults:` in the host file applies to every app; an app's top-level key overrides it key by key, and process keys can be overridden once more under `processes.<name>`.
* Values take `$NAME` from the daemon environment at load (uppercase only, unset names stay literal); `procfile` and cron commands are never expanded. A duration key takes a Go duration, a day count (`7d`) or `false`, which is `0`: off for the keys where `0` means off. In a web process's `hosts`, a leading `*.` matches subdomains only and a leading `.` matches the apex and its subdomains.
* Dboss injects `PORT`, `APP_NAME`, `PROC_TYPE`, `PROC_INSTANCE` and `DBOSS_SOCKET` into every process; `PORT` is the fixed port of the process's slot from `ports` and is never configurable. `dboss password` prints a bcrypt hash for `basic_auth`.
* Keys: `dboss config --keys [filter]` (one-line docs + defaults, grouped by block), `dboss config --reference` (long form, also `./internal/config/reference.yaml`), `dboss config [app] -d` (resolved config).
* `dboss init [service|app]` prints a fully commented starter config generated from the registry and the structs (`config.Template`); with no argument it asks with an up/down menu (falls back to a typed prompt when not on a terminal). The last line is the `dboss init > dboss.yaml` hint.
* Cloudflare is the preferred edge, not a requirement: TLS, compression, caching, WAF and rate limiting stay there when it is used. `proxy.cloudflare: true` makes `proxy.CloudflareOnly` refuse every connection outside the built-in `cloudflareRanges` (plus loopback) and makes `clientIP` read `CF-Connecting-IP`; without it the client address is the connection's own. Without Cloudflare, set `proxy.tls.listen` and dboss terminates HTTPS itself: `./internal/proxy/tls.go` obtains Let's Encrypt certificates on demand into `dir/state/acme`, plain http always redirects, and `hostAllowed` limits issuance to `management.host` and the hosts of the live apps, so a stranger cannot burn the authority's rate limit. A dev session serves HTTPS from `devtls` only under `dboss start --https`, on `:443` next to plain http on `:80`, never redirects plain http, and `Daemon.startDevProxy` fails when the authority or either port is unavailable; without `--https` it serves plain http on a claimed port. The banner prints one `https` row with the trust state (`Authority.Trusted` asks the system verifier).
* Management console is served on `management.host` and on `127.0.0.1:<console port>`: the first port of `ports` on a host, a claimed port in a dev session. `daemon.Build` stores it in `config.Config.ConsolePort` (runtime only, carried across `Manager.Rescan`). `config.Config.ConsoleEnabled` decides whether it exists at all, and `config.Config.ConsoleURL` is the address hook URLs are built from. Production sign-in is AuthCog (`authcog_realm`, default `auth.authcog.com`, `management.admins`, lasting `defaults.session_ttl`); `dboss login` mints one one-time token and prints both the loopback URL and the public `https://<first management.host>` URL, so a browser at the edge can sign in without an SSH tunnel. The public address is always `https://<first management.host>` (`management.PublicURL()`).
* App-level changes apply on `dboss rescan`, and so do `tokens`, host `pages` and `authcog_realm` for the proxy (read per request from `Manager.HostConfig()`); `apps`, `dir`, `ports`, `log_level`, `audit_retention`, `maintenance_at`, `proxy`, `management` and `notify` need a daemon restart (`config.RestartRequired`).

## Working rules

* Build with `make build`; `~/bin/dboss` is a symlink to `./bin/dboss`, so a rebuild is what the shell runs.
* Validate with `make check` (vet, staticcheck and tests). Add a test next to the package you change.
* The demo host is `./demo/dboss.yaml`; run it with `make demo` or `dboss start` inside `./demo` (`-y` skips the ENTER prompt). It listens on `:80` and needs no `sudo`: the terminal fallback moves the proxy into `ports` when the bind is refused, and the banner names the address every app got. Never put `sudo` back, it is what leaves `./demo/.dboss` owned by root.
* Console static assets are embedded with `go:embed`. A CSS or component change needs a rebuild and a daemon restart to show up.
* Do not add Docker or rate limiting, and keep deploy logic in `dboss deploy` and hooks. Cloudflare is the preferred edge. TLS is the one exception: a host session uses on-demand ACME through `proxy.tls`, no certificate files, no manual renewal. A dev session (`cfg.Dev()`) never uses ACME; `./internal/devtls` is its built-in local authority, one root per user under the user config directory (`devtls.DefaultDir`), leaves signed in memory per requested host, and `dboss trust` puts the root in the system store. A hand-run dev start asks first (`CLI.offerTrust`, terminal stdin only) and never refuses to start over it.
* Config is real YAML on disk. Never introduce a database copy of the config.
* `dboss.yaml` is the only config file name; `dboss.local.yaml` is the server-only override and is gitignored.
* A new config key needs an entry in `keySpecs` in `./internal/config/keyspecs.go` naming its block, a short name and a one-line description (plus an enum, an example when a second value helps, and the required/secret flags when they apply); the test fails otherwise. Path, type, types, per-process and default are read from the structs and `Default()`. Blocks and their scope live in `./internal/config/schema.go`. Add the key to `reference.yaml` for the long-form text; `reference_test.go` fails until it appears.
* State files under `dir/state` (`running.json`, `maintenance.json`, `last_activity.json`, `created.json`) are written by the daemon only.
* Shared helpers, so a new feature does not grow another copy: `fsutil.WriteFile`/`WriteJSON`/`ReadJSON` for every daemon state file (atomic, exact mode), `secret.Store` for generated pubsub secrets, `schedule.Daily` for a daily HH:MM job (local time), `module.Ticker` for a module that runs one pass on an interval, `fsutil.HumanBytes` for a size in a message, `config.NormalizeHost`/`BestMatch`/`PrimaryHost` for host handling (`./internal/config/hosts.go`) and `httpx.BearerToken` for bearer credentials.

## Modules and the request pipeline

* `./internal/daemon` is the only place a session is assembled: supervisor, `module.Manager`, proxy, console and control socket. `cli.start` loads the config and calls `daemon.Build`, `Serve` (modules, banner), then `Boot` (apps) after ENTER, `-y` or at once without a terminal. Register a new module there, not in the CLI.
* `supervisor.New` only discovers apps and assigns ports; `Manager.Boot` starts the desired apps and the idle and cron loops. Until then `Manager.Wake` is a no-op and `Manager.Booted` is false, so the proxy answers a stopped app with the self-reloading `waiting` page (press ENTER), never the starting page, and the console's `capabilities.held` raises the red `.held-bar` in `db-shell.fez`; an explicit start from the console or `dboss run` still works. A test that expects autostart calls `Boot`.
* Dev ports: a host owns `ports` (`ports.ClearPortRange` in `Build`, `ports.New` counting up). A dev session shares it with other app folders through `./internal/ports/registry.go`: one `<user config dir>/dboss/sessions/<pid>-<id>.json` per live session, claims serialized by an flock on `sessions.lock`, dead sessions dropped by the next claim, busy ports skipped (`ports.Free`), and the folder's previous ports (`state/ports.json`) preferred. `ports.NewClaiming` routes every `Allocate` there. A dev start clears only `Registry.Stale` (its folder's previous ports no live session holds), `spawn` skips `ClearPort` in dev, and `dboss kill` in an app folder clears only `ports.Recorded`. `devSessionsDir` is the test seam.
* A long-running feature implements `module.Module` (`Name`, `Start`, `Close`) in `./internal/module`. `logstore.Store`, `./internal/ingest`, `./internal/alerts`, `./internal/tmpclean`, `./internal/diskusage`, `./internal/sysinfo`, `./internal/pg` and `./internal/pubsub` are the current modules.
* `./internal/tmpclean` is the daily sweep of each app's `./tmp`, driven by the `tmp_clean` age on `Snapshot.TmpClean` (`0` or `false` skips the app). It sweeps once on start and every 24h: files older than the cutoff go, then the directories the sweep emptied and the ones already empty and as old, never `tmp` itself. `Sweep` resolves the path first, so a `tmp` symlinked to a shared directory is followed.
* `./internal/diskusage` is the per-app footprint: the app directory plus `dir/log/<app>`, walked once on start and every 24h and cached per app, with `Refresh(app)` for the console's click-to-measure (a walk already running for that app answers from the cache instead of queueing another). `ops.Service` holds it as its `Disk` dependency and fills `Snapshot.Disk` in `Apps`/`App`, so the console, `/metrics` and `dboss status --json` can never disagree; the supervisor never walks, because `snapshot()` runs on the app goroutine. `dirBytes` skips the resolved `log_dir/<app>` while walking the app, which is what keeps a single-app session (where `log_dir` sits inside the app folder) from counting the log store twice. Sizes are apparent size and only the two roots are symlink-resolved, so a shared directory is never billed to two apps.
* `./internal/sysinfo` is the read-only host inspector behind the console's Sys tab: OS, kernel, load, memory, disks and a fixed toolchain probe list. `daemon.Build` registers its `Module` and hands `Inspector()` to `console.New` as a `SysReader`. It never mutates dboss state and writes no audit row; add a tool by adding a `probe` to `defaultProbes`. A fact that has to be fetched from off the box goes through a `remote` (`Inspector.release`, `Inspector.echo`): it keeps its answer for `defaultRemoteRefresh` (1h) behind a 4s timeout and stamps every attempt, a failure included, so an unreachable service leaves the field empty instead of stalling each refresh. `Runtime.DbossLatest`/`DbossLatestURL` are `release.Latest`; `Host.PublicIP` is `./internal/sysinfo/publicip.go`, which prefers the box's own routable interface address (`routable` drops loopback, link-local, RFC 1918, ULA and RFC 6598) and only asks `echoURL` when there is none, so a server costs no request and a NAT box still reports an address.
* `./internal/pubsub` is the realtime channel hub behind each web process's `pubsub` option (`true` -> `/socketio`, a path, or a setting mapping). `resolvePubsub` resolves it onto the runtime `config.WebProcess.Pubsub`, so it rides `Snapshot.WebProcesses`; there is no top-level or `web` pubsub key. It is served by `Service.Filter`, registered as a proxy extra stage; `Service.AuthorizesPublish` lets a publish secret satisfy the proxy's `authorize`. It keeps one hub per `(app, process, channel)` and stores generated secrets in `dir/state/pubsub-secrets.json`. The browser client and self-test are embedded (`client.js`, `test.html`); the integration guide is `pubsub.Help`, shared by `dboss pubsub help` and the console Help tab. Reserved segments are `client.js`, `_test`, `_selftest`. Long-lived subscribe requests call `SuppressRecord` so a socket's lifetime never skews request latency.
* `warnUnignoredRuntime` in `./internal/cli/gitignore.go` warns a terminal session when the runtime folder (`runtimeRoots`: the runtime `dir` when it sits inside the config dir, normally `.dboss`) would be committed. It only speaks when that directory has its own `.gitignore`, and asks `git check-ignore` with a trailing slash so a directory-only rule matches before the folder exists. Any error, including no git and no repository, stays silent; it must never block a start.
* `./internal/daemon/banner.go` is the startup summary of a hand-run session, gated on the same `echo != nil` terminal signal as the output echo: one row per process keyed by `Echo.Key(app, proc)`, so the row and that process's later log lines share a color. In single-app mode (`cfg.App != nil`) `cli.start` calls `Echo.Solo`, which drops the app segment from every key, so a run inside an app folder prints `job |` rather than `sinatra/job |`; `Echo.Name` is the uncolored label the banner measures its columns with. It opens with `bannerIntro` (`dboss <version> - dev session for <app>:` or `- host <dir>:`) and prints after the ready log, right above the ENTER prompt. A web process shows `webURL` (canonical host, else the first concrete host, else a leading-dot pattern's apex; a `*.`-only pattern gets no link), a worker shows `worker`, and `bannerNote` only adds `maintenance`: the banner always prints before any app starts. The first row is the console, with the note `printBanner` passes as `banner`'s `consoleNote`: a dev session prints `cfg.ConsoleURL()` and `open on this machine`, since it needs no token, and a host session prints `console.Handler.DevLoginURL`, an hour-long reusable loopback token (`issueDevToken`, `cliToken.reusable`) that is never minted under systemd, unlike the single-use 3-minute `dboss login` link.
* Every listener is opened by `bind`/`bindProxy` in `./internal/daemon/daemon.go`; `startHTTPServer`/`startHTTPSServer` only serve an already-bound listener. A refused privileged port names root, `CAP_NET_BIND_SERVICE` and the config key that moves it. `bindProxy` adds the terminal-only fallback: when stdout is a terminal (`echo != nil`, the same signal `cli.start` uses for the output echo) a `proxy.listen` address the process may not bind moves to the first free `ports` port from the allocator, and `Daemon.listen` records the effective addresses for the ready log. TLS and the management console never fall back; under systemd nothing does. A dev session does not use `bindProxy`: `startDevProxy` binds a claimed port, or exactly `:80`/`:443` under `--https` (`devBind`, fatal when taken). `netListen` is the test seam.
* The proxy pipeline is an ordered `[]proxy.Filter` built in `proxy.initFilters`. A new request filter is a function of that shape, inserted before the forward stage; the built-ins live in `./internal/proxy/filter.go`.
* A procfile entry runs `count` instances (`./internal/supervisor/instances.go`): `web` when count is 1, else `web.1`..`web.N`. The instance name keys `appRuntime.processes`, `ready`, `failures` and `held`, the log file and the snapshot row (`ProcessSnapshot.Name`, with the entry in `Type`). Each live process sits in a slot (`web`, `web#1`, ...) that owns its port, cgroup directory and pid file; `assignPorts` allocates one slot per instance plus one spare for a web process, and `spawn` takes the first slot no tracked process (live, retiring or roll replacement) holds. `spawn` returns the process untracked; `spawnOne` tracks it. `release` is the one cleanup path and keeps a log writer another copy still shares open.
* The proxy never scans snapshots for a port: `Manager.Pick(app, web)` reads the `routeTable` (`./internal/supervisor/routes.go`) the app goroutine republishes after every request and event (`publishRoutes`: ready instances only), picks the upstream with the fewest requests in flight and counts the request on it and on the app under the same lock a route change takes, so a port that left the route gets no new request.
* `Manager.Restart` on a running app with a web process rolls (`./internal/supervisor/roll.go`): the `start` lifecycle step, then per web instance a replacement spawned beside it and watched; its `ready` swaps it into `processes` and `retire`s the old one (out of the route, drain on its upstream counter, `stop_signal`, kill, then a `retired` event releases it), all off the app goroutine. Workers retire and respawn, never doubled. A replacement that exits or fails health aborts the roll (`abortRoll`): it is killed, the old copy stays, `health-timeout` is emitted and `Restart` returns the error; it waits on the roll through `request.done`. A restart asked for during a roll queues one more. `RestartProcess` on a web process or instance rolls just that; anything not running, with no web process, or a worker takes the plain path. `Manager.Stop` (and a plain restart) drains first: `requestDrain` sets the snapshot's `Draining`, new requests get 503, and `Manager.drain` waits on the per-app in-flight counter up to the host `stop_timeout`. Draining runs off the app goroutine, so snapshots stay responsive.
* `Manager.StartProcess`/`StopProcess`/`RestartProcess` act on one procfile process (every instance) or one instance of a live app, reached through `start`/`stop`/`restart` with `Request.Process` set (the app card's per-service buttons). Start and stop do not drain. A stopped instance goes into `appRuntime.held`, so `processExited` and a queued backoff restart leave it down until a process start, a roll, or the next app `start()`, which clears the set; it lives in memory only. A web instance that exits only moves the app to `starting` or `crashed` when no other instance of that web process is ready.
* `serveStatic` in `./internal/proxy/proxy.go` answers GET/HEAD from the matched web process's `Static` (default `./public`, `false` disables) only for `Web.StaticExtensions`; everything else, including an existing `.html` or dotfile, falls through to the app. An empty list serves any file.
* Every HTML page dboss answers with itself goes through `./internal/pages`: `pages.Specs` names each page (status, title, message, host-only or not), `Page.Render` reads `<name>.html` then `template.html` from the app's `Snapshot.Pages` folder, then the host's `pages` folder (`Handler.hostPages`), then the embedded `template.html`, and `Page.Fill` replaces only the known `{{...}}` tokens (`{{action}}` is dboss-built HTML, everything else is escaped). The proxy, the console login page and `dboss pages` (`./internal/cli/pages.go`, list and `dump` via `pages.Source`) share it; `pages.LogoPath` is answered by the proxy on every host before routing and by the console. `Handler.errorPage` always renders `error` for the proxy's own 502s; `replaceAppError` in `ModifyResponse` swaps an app 5xx body only when the app's own folder has `error.html` or `template.html`. Both act on `wantsHTML` requests only, so API answers are never rewritten.
* The proxy matches the request host to a web process with `Snapshot.WebForHost`, which drives the canonical redirect, the `Pick` of an upstream copy and the logged process. `forward` adds `X-Forwarded-Proto`/`X-Forwarded-Host`/`X-Real-IP` only when missing, so Cloudflare's values win. `startOrder` spawns every web process first, then the rest by name; `assignPorts` keeps its own name order.
* `./internal/res` is the resource backend seam. `Procgroup` (macOS and non-cgroup Linux) sums `ps` and ignores limits; `Cgroup` gives each (app, process) its own cgroup v2 directory under `/sys/fs/cgroup/dboss`, writes `memory.max`/`cpu.max`, reads `memory.current`/`cpu.stat`, and reads `oom_kill` from `memory.events` (`OOMKills`), which `oomCause` compares with the count at spawn before `release` removes the directory: an OOM kill writes a line into the process log, emits `oom` and suffixes the crash message. `selectCgroup` picks it when the hierarchy is writable and `resources` is not `procgroup`; a limit set while on procgroup logs a warning. `processEnv` in `./internal/supervisor/env.go` assembles the process environment in the documented priority order (daemon+mise, config env, `.env`/`.env.local`, then injected: `PORT`/`APP_NAME`/`PROC_TYPE`/`DBOSS_SOCKET`; `spawn` adds `PROC_INSTANCE`). Its three callers are `spawn`, `Manager.Exec` and the cron/hook runner.
* Actions reachable from both the CLI and the console belong on `ops.Service` (`./internal/ops`), not in either transport. A mutating action is unexported and reached only through `Do`, so no transport can skip its audit row; the exported methods are reads plus `SaveConfig`, `Audit` and the pg download/upload. `ops.New` takes one `LogStore` (rates, viewers, traffic, latency and audit together) and one `Notifier`. The github_pr preview deploy is `./internal/ops/preview.go` on top of `./internal/preview` (request params and template rendering) and `./internal/git` (token-authenticated clone and reset).

## Health and metrics

* The management host serves `/healthz`, `/readyz` and `/metrics` from `./internal/console/routes.go` before the session auth. `/healthz` and `/readyz` are always open; `/metrics` needs `tokens.dboss` (`ops.Service.DbossToken`, read live) as a bearer token and answers 404 without one.
* `./internal/metrics` renders Prometheus text from `ops.Service.Apps()` snapshots, so metrics and the console can never disagree. Add a metric there, not in the handler. `metrics.Render` takes one `metrics.Input` that `ops.Service.Metrics` builds; the latency quantiles are `logstore.Store.Window` over the last hour.
* `Web.HealthEndpoint` (default `/.well-known/dboss/health`) is answered by the `publicHealth` filter in `./internal/proxy/filter.go` before auth: 200 while `Snapshot.Serving()` (running, or stopped and woken by the next request), 503 when draining, in maintenance, starting, crashed or a stopped button app; it never wakes the app. `/readyz` uses the same `Serving()` for autostart apps. `dboss doctor` uses `supervisor.ListenersInRange`, which returns one `supervisor.Listener` per socket (pid, command, bound address) from `lsof -Fpcn`: the doctor warns about the range not being clear and, separately, about any listener whose `Loopback()` is false and whose command is not `dboss` itself. An app binds its own port and the proxy only ever dials `127.0.0.1`, so a public bind answers without `basic_auth`, `allow_ips`, the sign-in gate or the `X-Dboss-User` strip; dboss never passes a bind address, so binding loopback is the app's job.
* Every web process is monitored for its whole lifetime by `appRuntime.monitor` in `./internal/supervisor/health.go`: `health`/`health_timeout` gate readiness, polled every `healthInterval` (500ms, a var only so tests can poll faster), then the ticker is reset to `appRuntime.livenessInterval` (`liveness_interval`, default `10s`) so a ready app is not polled at the readiness rate forever, and `unhealthy_threshold` consecutive failures emit `health-failed`, which kills the process so the normal exit path restarts it under `restart`/`backoff`/`max_restarts`. `0` disables liveness; workers are not polled. `livenessInterval` raises the period to `devLivenessInterval` (5m) when `a.echo != nil`, the same hand-run signal as the banner; it only ever slows the check down, and the echo is a session property so a rescan cannot lose it.
* `./internal/version.Version` is `v<number of commits in main>` and nothing else. `make build` injects `v$(git rev-list --count main)` with `-ldflags -X`, and `./.github/workflows/release.yml` injects `v$(git rev-list --count HEAD)` from a `fetch-depth: 0` checkout, so the tag name no longer decides the version. A plain `go build` leaves it at `version.Dev` (`dev`), which is what marks a from-source binary; `String()` has no fallbacks.
* `./internal/cli/update.go` is `dboss update`, the Go port of `./install.sh`'s download half: resolve `releases/latest` through the GitHub API, download `dboss_<GOOS>_<GOARCH>`, verify its sha256 against the release `checksums.txt` and `os.Rename` it over the executable (a running binary cannot be written to, only replaced). Staging is a temp dir next to the target so the rename stays on one filesystem. The repo never stores a version file: a commit-tracking file would name versions that have no release asset. `./internal/release` is the release source itself - `Repo`, `APIBase`, `DownloadBase` (the test seams), `Latest`, `AssetURL`, `TagURL`, `Get` and `Number` - shared with the console's Sys tab, so nothing else may name the repository. It refuses a `dev` build and an unwritable directory instead of elevating itself, and never restarts the daemon.

## Audit and config history

* `ops.Service.Do` writes one `audit` row per mutating action through the `LogStore` (a nil store disables auditing). Transports set `Request.Actor`: console = session email, hook ping = `hook:<app>/<hook>`, control socket = `cli`. Config writes go through `ops.Service.SaveConfig` (write, rescan, audit, `config-changed` notify); the CLI's `dboss config restore` is an offline file edit and is not audited.
* Audit rows live in the reserved `_dboss` database (`audit` table), pruned by `audit_retention` in `logstore.Prune`.
* `apps.Store.Write` snapshots the current file to `dir/state/config-history` first, keeping 50 per file; `History`/`HistoryContents`/`Restore` back the console History panel and `dboss config history|restore`. Restore is a normal revision-checked `Write`.

## Notifications

* `notify:` in the host config points at one operator webhook. `./internal/notify` debounces per app and event, queues with a bounded buffer and posts best-effort, so it can never block the supervisor.
* `daemon.Build` creates the notifier and passes it to `supervisor.New` (as a `notify.Sink`) and to `ops.New` (as an `ops.Notifier`, which also reads its counters for `dboss_notifications_total`). `Manager.Wake` is the proxy's start path and the only source of `wake-failed`; explicit run/console starts do not notify.
* Events are emitted by `appRuntime.emit` in `./internal/supervisor`: `crash`, `restart-loop`, `health-timeout`, `hook-failed`, `cron-failed` (a cron job exited non-zero, timed out or could not start), `oom` and `deploy` (a `restart: true` hook succeeded). `ops.Service.SaveConfig` covers `config-changed` from the console. `./internal/alerts` is the module behind `error-rate` and `slow`: once a minute it reads `logstore.Store.Window` for every app whose `alerts:` block (`config.Alerts` on `Web`, so it rides `Snapshot.Web`) has a check on, and sends straight to the sink; it keeps no state, the notifier's `min_interval` bounds repeats. The same pass posts one host-level `disk-low` naming every filesystem (deduplicated by `sysinfo.Dir.Device`) of the `sysinfo` dirs past the live `disk_alert` percent. A new event needs a constant and an entry in `notify.Events` in `./internal/notify/notify.go` (config validates `notify.events` against it) and a line in the reference.

## Log store

* One SQLite database per app at `dir/log/<app>/dboss.sqlite`: `requests`, `logs` and the `logs_fts` FTS5 index, plus `tail_offsets` for the file tailer. `./internal/logstore` owns the schema, batching, search and prune. `requests.request_id` is the `CF-Ray` when present and is covered by the request search; `requests.country` is `CF-IPCountry`. A new `requests` column needs the `CREATE TABLE` entry and a best-effort `ALTER TABLE` in `writer()`.
* `logs.source` is the channel: `stdout` (process output), `dboss` (dboss's own daemon log, in the reserved `_dboss` database), or `file` with `logs.process` holding the app log path. `log_retention` prunes requests and `file` rows; `stdout_retention` prunes `stdout`/`dboss`.
* The supervisor writes through `supervisor.logWriter`, which owns the file, rotates by size and can `Seal` a segment; `Manager.SealLogs` exposes it. Do not rename a live process log from outside the supervisor.
* `./internal/ingest` seals stdout segments and tails every `*.log` under `<app dir>/log` every `logIngestInterval` (5s, `./internal/daemon`). App log files are app-owned: track offsets, never delete them. Parse changes belong in `ingest.ParseLine` (one line) and the `grouper` in `./internal/ingest/group.go` (which lines form one row: leading whitespace, the Rails `Started`..`Completed` block, the `[request id]` tag, blank lines, the row cap). A row still open in a log written to within `tailQuiet` is held back: the file tailer keeps its offset at the row start, and `ingestSealed` rewrites the newest segment to just that row (`carryTail`). `appRuntime.sealLogs` returns every `*.sealed` file on disk, so a segment left by a failed commit is retried. It commits through `logstore.AppendLogs` (synchronous) and only deletes a sealed segment or advances an offset after that commit succeeds, so a transient database error cannot lose rows or duplicate reads.
* `logFlush` in `./internal/daemon` (1s) is the one batch-insert interval of every app writer. `log_retention` (default `336h`) covers requests and app log files; `stdout_retention` (default `3h`) covers stdout and the dboss daemon log; `log_retention: 0` disables the whole store for the app. The `dboss.sqlite` name is fixed; there is no config key for it.
* `maintenance_at` (default `04:10`) is the one daily housekeeping time: `Store.Start` runs the prune and then SQLite `VACUUM` on every app database and the host database (`Store.Vacuum`), so the vacuum reclaims what the prune freed.
* Prune and vacuum walk every database on disk (`Store.diskApps`), not just the current snapshots, so a database left behind by a removed app is still bounded. A failed insert keeps its batch for the next flush, capped; `AppendLogs` is the synchronous path for rows that must not be re-read.

## PostgreSQL

* `./internal/pg` owns the read-only inspector and the backup engine behind the console's PostgreSQL tab. `daemon.Build` builds one `pg.Service` (a `module.Module`), registers it and passes it to `ops.New`; every PG action goes through `ops.Service`, so the CLI and console share it.
* Connection resolves `postgres.dsn`, else the unix socket (`/var/run/postgresql`, then `/tmp`), else `127.0.0.1:5432`, with the libpq `PG*` environment merged by pgx; under sudo it impersonates `SUDO_USER`, since root has no matching role. A failed detection logs one warning and leaves the tab hidden. The service keeps a short-lived connection per inspection and a `connConfig` for the external `pg_dump`/`psql`, whose password travels in the child environment, never argv.
* The inspector writes nothing and audits nothing. `pg.Service.BackupAll`/`BackupDatabase` run `pg_dump --format=plain`, zip the result to `pg_backup/<database>/BACKUP_<timestamp>.zip` under the config dir and record a row in `dir/state/pg-backups.json` (never in SQLite). An explicit `BackupDatabase` is manual, so `prune` never removes it. `uniqueDump` names every archive, so two dumps of one database in the same second cannot share a file or an id.
* `pg.Service.BackupFile` and `ImportBackup` are the console's download and upload: the archive travels as it is, an upload is validated as a readable zip, stored under the named database and recorded as a manual entry, so it restores through the normal path. Both ride `ops.Service` and audit through `Service.Audit` (`pg-download-dump`, `pg-upload-dump`) rather than `Do`, since the upload carries an `io.Reader` that does not belong on the JSON `Request`. The routes are `GET /api/pg/backup/download?id=` and `POST /api/pg/backup/upload?database=` (multipart, streamed to disk, bounded by `maxBackupUpload`, not the JSON body cap).
* Retention is the pure `keepSet` in `./internal/pg/retention.go`: scheduled dumps survive while newer than their database's rotation window (`week`/`month`, `rotationWindow`), manual dumps always. `prune` removes files and catalog rows beyond the window; failed entries stay for visibility until the catalog cap drops them.
* `pg.Service.Query` is the console's SQL runner: one fresh connection to the named database, `SET statement_timeout` at 30s, and `conn.PgConn().Exec`, so a pasted batch runs statement by statement and the last result set is what comes back. Every value is the server's text form (a NULL stays nil), 500 rows travel while the full count is still reported, and one cell is capped at 10k chars. It runs any SQL, so it goes through `Do` (`ops.Service.runQuery`): `ActionPGQuery` is in `auditActions` and `auditDetail` records the database plus the one-line `pg.QueryAuditDetail` form of the statement.
* `ops.Service.dropDatabase`/`pg.Service.DropDatabase` drops a database through the maintenance connection, refusing `postgres`/`template0`/`template1` and requiring the name as confirmation. Restore unzips the archive and runs `psql`; `--replace` drops and recreates the target.
* `postgres` is a host key but hot-reloads: the console's `POST /api/pg/config` writes the selection to the host `dboss.local.yaml` (created from the base when missing) and goes through `ops.Service.SaveConfig`, whose rescan re-applies `Manager.HostConfig()` to `pg.Service`, so no daemon restart. A plain edit on disk applies on the next config save or `dboss rescan`. `Manager.Rescan` loads `config.Live(SourcePath)`, so a `dboss.local.yaml` created next to the base after start wins from the next rescan.
* Runtime deps on the box: `pg_dump` and `psql` on the service user's `PATH`, and a role that can read every selected database.

## Console frontend (fez)

* Components live in `./internal/console/static/fez/`, one component per file. Shared widgets (`db-*`) are loaded from `index.html` with `<script fez="/assets/fez/<name>.fez">`; route pages (`tpl-*`) are fetched per route by `db-shell`. Do not switch to a multi-component `<xmp fez>` file.
* Console pages are hash routes on `/` (`#/overview`, `#/traffic?app=x`). `db-shell.fez` reads `Pjax.hpath()`, renders `tpl-<name>` into `#route-outlet`, and drives the nav from its `ROUTES` list. Page state lives in the hash query via `Pjax.hqs`/`Dboss.setQs`, so reload, Back/Forward and deep links reproduce the page; `#foo` stays a native anchor.
* Read `~/dev/gems/fez/AGENTS.md` before editing any `.fez` file.
* Fez replaces a component tag with `<div class="fez fez-<name>">`; style that wrapper, not the custom tag.
* All CSS lives in `./internal/console/static/app.css`; components have no `<style>` blocks. Keep the light Tabler-style tokens defined on `:root` there.
* No external assets: the CSP allows only the console's own origin. `fez.min.js` is vendored; update it by copying https://dux.github.io/fez/dist/fez.min.js, never below 0.10.0 (`TestVendoredFezIsCurrent` fails on an older one). That build removed the root attribute observer, which fed a component's own root writes back into its props and re-entered `ui-btn`, and it added `Fez(node).setAttribute`. The Pages URL can lag behind `~/dev/gems/fez/dist/fez.min.js`; take the newer of the two.
* A `.btn` is disabled by the `disabled` attribute, never a class: a `span`, an anchor and a label have no native disabled state, so `.btn[disabled]` is what greys it out and stops the click. `ui-btn.fez` owns that attribute. The template compiler keys every placeholder it emits, so a `ui-btn` is preserved across a parent render and never has its root attributes synced; it re-applies every prop in `paint()`, called from `init` and `onRefresh`, with `props` the only source. `onclick` is repainted too: it is rewritten to `Fez(<uid>).method(<args>)` on every parent render, so a preserved button that repainted only its label would keep calling the previous render's arguments. A card shows an action as pending with its own `state.pending`, one more term in each mutating button's `disabled` expression, so the flag and the next snapshot land in the same render. A component that must react to a changed prop uses `onRefresh`; `onPropsChange` no longer exists.
* Cross-component calls go through the globals `Dboss` (shell: `api`, `readQs`, `setQs`, `reload`, `runAction`, `rescan`, `logout`), `Toast.show(message, error)` and `Drawer.open(title, text)`. Shared data lives in `globalState` (`apps`, `loaded`, `busy`, `status`, `restartRequired`).

## Deploy hooks and one-off commands

* Hooks are named one-shot commands under `hooks:` in the app file, triggered by a signed POST to `/hooks/<app>/<hook>` on the management host. The endpoint lives in `./internal/console/hooks.go:handleHook` and runs before the session auth; its own secret is the credential (query token, bearer, `X-Gitlab-Token`, or a GitHub HMAC over the raw body).
* Every hook ping, app or host, presents `tokens.dboss` from the live host config (`Manager.HookToken`/`HostHookToken`, which also answer unknown hooks with an error for the 404); an unset token refuses every ping, including a GitHub HMAC made with the empty key. There is no per-hook secret and nothing to rotate: the operator changes the token in the file and runs `dboss rescan`. `Manager.Hooks` is the only path that carries the token (in the ping URL) and is kept off the regular snapshot. Generated secrets in `./internal/secret` are pubsub's only (`dir/state/pubsub-secrets.json`).
* Hooks reuse the cron runner (`jobState`/`jobRun` in `./internal/supervisor/cron.go`); both live in `a.cron` and `a.hooks`. Output goes to a `hook-<name>` channel. `restart: true` restarts (or starts) the app after a clean exit; the hook reads `restarting` from that exit until `a.restart` returns (the `hook-restarted` event), and a failed restart becomes its `LastError`. A hook keeps the last 8 KiB of its last run's output (`outputTail`), carried only on `HookInfo.Output` (the hooks view and the status route), never on the regular snapshot.
* `lifecycle:` in the app file holds the `create`, `start` and `destroy` steps (`config.LifecycleCommand`, parsed to `apps.Step`). `create` and `start` are `jobState`s of kind `lifecycle` in `a.lifecycle`, run by the cron runner: `appRuntime.start` sets `Starting` and calls `continueStart`, which runs create (only while the app is not in `dir/state/created.json`), then start, then `spawnAll`; `jobExited` hands a finished step to `stepExited`, which records create through `Manager.markCreated` or calls `failStart`. `stop` kills a running step with `stopSteps`. `destroy` runs in `Manager.runDestroyStep` after the runtime is closed and before the folder is removed, through `Manager.run` (the body `Exec` shares); a failure is logged and notified as `hook-failed`, never blocking the destroy. The github_pr hook has no setup step: a preview's template declares its own `lifecycle`.
* `dboss exec` runs off the app goroutine via `Manager.Exec`; it only reads the immutable spec through `requestExecInfo`, so a slow command cannot stall the supervisor.

## Console auth

* `./internal/authcog` is the AuthCog flow shared by the console and the proxy: challenge map, callback exchange (`Flow.Exchange` is the test seam), signed session cookie and the `dir/state/management-auth.key` key. A caller describes itself with an `authcog.Gate` (audience, AuthCog `Realm` host, hosts, callback path, cookie names, TTL, `Allow`). The session payload carries the gate's `Audience` (`console`, `app:<name>`, `authcog:<name>`) and `Flow.Session` rejects any other, so a console cookie never opens an app and an app cookie never opens another app. `Flow.Authenticate` verifies the callback and returns the profile without a session; `Flow.Callback` is it plus the console's session cookie. Whether an email may still enter is the caller's check on every request.
* The proxy's per-app gate is the `signIn` filter in `./internal/proxy/signin.go`, between `authCog` and `authorize`, driven by `Web.Auth` (the `auth:` email list) and `Web.SessionTTL`, against the host `authcog_realm`. It answers `/.well-known/dboss/auth` and `/.well-known/dboss/logout` (the `signed_out` page) itself, sets `X-Dboss-User` to the signed-in email, honors `AuthorizesPublish`, and answers 401 instead of redirecting when the request is not `wantsHTML`. It skips the `authcog` login path so an app can use both.
* The app-level AuthCog login service is the `authCog` filter in `./internal/proxy/authcog.go`, between `publicHealth` and `signIn`, driven by `Web.AuthCog` (`config.AuthCogPath`: `authcog: true` is `/authcog`, a path sets it, false is off) against the host `authcog_realm`. It captures that path: no `callback` starts the flow, a `callback` runs `Flow.Authenticate` and then forwards the request to the app with the profile as JSON in `X-Dboss-User`, and the app creates its own session. `serve` deletes `X-Dboss-User` from every inbound request, so only dboss sets it. It is independent of `auth`.
* `./internal/console/auth.go` holds both sign-in paths: AuthCog (admins only) and `dboss login` (`/login?token=`, 3 minutes, single use, signs in as `cli@localhost`).
* `cli@localhost` is accepted only for sessions created by a token, or handed out directly by a dev session. The AuthCog callback must keep rejecting it.
* A dev session (`cfg.Dev()`) needs no sign-in: `authenticate` returns `authenticator.devSession` for any request whose `loopbackPeer` is true, before the `/api/` 401 and the AuthCog redirect. That session is minted once in `consoleAuthenticator` and never written to a cookie, so its CSRF token cannot drift under a console that read it at boot; `POST /api/logout` is therefore a no-op there and the console hides the button on `capabilities.dev`. `validateManagement` drops the `management.admins` requirement in dev for the same reason. `loopbackPeer` reads `RemoteAddr` only, never a forwarded-for header, so an app-mode dboss must not sit behind a reverse proxy on the same box.
* `Flow.Start` sends the browser back to where the request arrived: `authcog.Destination` builds `/d:<host>`, adds `/p:<port>` unless it is the scheme's default and `/s:http` unless the request was https. `authcog.Scheme` is the one scheme rule (TLS, else the edge's `X-Forwarded-Proto`, else http) behind the destination, the Secure cookie flag and the console's Origin check; nothing rewrites the login host.
* The console answers for `management.host` and for loopback names (`127.0.0.1`, `localhost`). A loopback request without a session gets a "run dboss login" page, never an AuthCog redirect. `dboss login` prints both URLs from `Handler.LoginURL`: `http://127.0.0.1:<console port>` and `https://<first management.host>`, sharing the one-time token.
* The login link is minted through the control socket (`login` method in `./internal/ctl/server.go`), never over HTTP.
